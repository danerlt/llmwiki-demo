01 · 概念定义

什么是 LLM Wiki?

LLM Wiki 是 Karpathy 在 2025 年的一个 Gist 中提出的知识管理模式: 不在每次提问时去检索原始文档,而是让 LLM 增量地构建并持续维护一个持久化、结构化、相互链接的 Markdown Wiki, 查询时直接阅读这个"编译好的知识制品"来回答问题。

"人类负责挑选资料和提出问题,LLM 负责所有繁琐的知识维护工作——更新交叉引用、保持几十个页面的一致性、标记矛盾。 维护知识库是人类总会放弃的枯燥簿记,而这恰恰是 LLM 擅长的机械劳动。" —— 核心思想:Human curates, LLM maintains
📜

思想源头:Memex(1945)

Vannevar Bush 在 1945 年设想的"记忆扩展器":个人化、可关联的知识存储,文档之间有"关联轨迹"。它失败于维护成本——LLM Wiki 用 AI 解决了这个 80 年的老问题。

🧠

范式转变:从工具到基础设施

把 AI 从"一次性改写器"(回答完即丢弃)重构为"可复用的、单一事实来源的知识层"。每次提问的好答案会沉淀成新的 Wiki 页面,知识产生复利。

📐

知识"编译"

类比编程语言:RAG 像解释执行(每次查询现场计算),LLM Wiki 像提前编译(AOT)——在摄入(写入)时就完成理解、消歧、关联,把成本前置。

02 · 三层架构

三层结构:Schema / Wiki / Raw Sources

整个系统只是文件夹里的纯文本,但职责被严格分成三层,数据流向单向且清晰。

⚙️ Schema(配置层)人类定义 · LLM 遵守

一份规则文档(如 CLAUDE.md / schema.md),规定 Wiki 的目录结构、命名约定、页面模板与操作流程。它把一个通用聊天模型变成有纪律的"知识管理员"。

⇅ 约束

📖 Wiki(知识层)LLM 完全拥有 · 持续演化

LLM 维护的 Markdown 目录:每个来源的摘要页、实体页(人物/组织)、概念页、跨来源综合页;用 [[wikilink]] 互相链接;index.md 是总目录,log.md 按时间记录每次操作。

↑ 摄入(只读原始资料,从不修改)

🗄️ Raw Sources(原始层)不可变 · 终极事实来源

你挑选的文档、论文、文章、网页剪藏、会议记录。LLM 只读不写,任何时候都可以回溯校验,Wiki 页面通过引用指回这里。

典型目录结构

my-wiki/
├── purpose.md            # 这个 Wiki 的目标与研究范围
├── schema.md             # 结构规则(Schema 层)
├── raw/sources/          # 原始文档(不可变)
├── wiki/                 # LLM 生成与维护的内容
│   ├── index.md          # 全部内容的目录
│   ├── log.md            # 操作流水账
│   ├── entities/         # 实体页:人物、组织、产品…
│   ├── concepts/         # 概念页:理论、技术、方法…
│   └── synthesis/        # 跨来源综合分析
└── .llm-wiki/            # 应用配置、对话历史
03 · 三大核心操作

Ingest · Query · Lint

整个模式只有三个动词。点击切换查看每个操作的内部步骤。

添加一个新来源时,LLM 不是简单"建索引",而是真正读懂并整合:

通读来源,结构化分析

提取关键实体、核心论点、与已有 Wiki 内容的关联点和潜在矛盾(实现上常拆成"分析 → 生成"两阶段思维链)。

生成来源摘要页

为该文档创建一个带引用回溯(指向 raw/ 的页码或段落)的摘要页面。

更新 10~15 个相关页面

新信息被"摊"进已有的实体页、概念页:补充事实、强化交叉引用 [[wikilink]]、合并重复表述。

标记矛盾,待人裁决

新来源与旧知识冲突时,LLM 不擅自二选一,而是显式标记出来供人审阅(async review)。

更新 index.md 与 log.md

目录登记新页面,日志记录本次操作,保证整个 Wiki 可审计、可回放。

提问时,LLM 读的是Wiki 页面而不是原始文档:

定位相关页面

从 index.md 出发(或借助关键词/向量检索),找到与问题相关的少量 Wiki 页面。

沿 wikilink 扩展上下文

顺着页面间的链接把关联概念一起读入,获得跨文档的全局视角。

综合作答并带引用

基于结构化页面合成答案,引用链一路可追溯到原始来源。

好答案沉淀为新页面 ★

这是与聊天机器人最大的不同:有价值的回答写回 Wiki,成为下次查询的素材——知识复利,而非消失在聊天记录里。

像代码 lint 一样,定期对整个知识库做健康检查:

矛盾检测

不同页面对同一事实的表述是否冲突?

过期信息

哪些结论已被更新的来源推翻或修正?

孤立页面与断链

找出没有任何入链的"孤儿页"、指向不存在页面的死链。

知识缺口

哪些概念被反复引用却没有自己的页面?哪些问题值得补充新来源?——Lint 的输出反过来指导人类去补充资料。

05 · 开源实现拆解

同一模式,两种工程路线

Karpathy 的 Gist 刻意保持抽象,只给模式不给代码。两个社区实现选择了截然不同的工程化路径,对照阅读能看清模式的边界与自由度。

github.com/nashsu/llm_wiki

nashsu/llm_wiki — 重型桌面应用路线

Tauri v2(Rust)+ React 19 跨平台桌面应用,把模式做成开箱即用的产品,内置图谱可视化与多种增强。

  • 两阶段思维链 Ingest:先结构化分析,再生成/更新页面
  • 混合检索:分词(CJK 二元)+ LanceDB 向量 + 图谱扩展 + token 预算分配
  • 四信号知识图谱 + sigma.js / ForceAtlas2 可视化,Louvain 社区发现
  • 异步 Review 队列:矛盾与不确定项交人裁决
  • Chrome 剪藏插件、文件夹自动监听、多模态图片摄入
  • 本地 HTTP API + MCP Server(:19828),供外部 Agent 查询
  • Obsidian 兼容 vault:[[wikilink]] + YAML frontmatter
github.com/lucasastorian/llmwiki

lucasastorian/llmwiki — 轻型 MCP 工具路线

FastAPI + Next.js + MCP Server,自己不调用 LLM,而是把工作区"暴露"给 Claude,让 Agent 亲自动手读写 Wiki。

  • 文件系统是事实来源,SQLite 只是可重建的检索索引
  • SQLite FTS5 全文检索(Porter 词干化),无向量库
  • MCP 工具集:guide / search / read / create / edit / append / delete
  • 工作流:init → serve → mcp-config → 连接 Claude →"摄入并建 Wiki"
  • pdf-oxide(Rust)抽取 PDF,可选 Mistral OCR 增强
  • 可托管部署:Supabase + PostgreSQL + S3(llmwiki.app)

06 · 对比传统 RAG

与传统 RAG 的本质区别

一句话:RAG 把计算放在查询时,LLM Wiki 把计算放在写入时。 RAG 每次都从生肉开始现炒;LLM Wiki 提前把食材做成了随取随用的预制菜谱,而且菜谱会越写越好。

07 · 优缺点分析

什么时候该用,什么时候别用

✦ LLM Wiki 的优势

  • 完美召回:不切块、不嵌入,小语料下没有"检索漏掉关键信息"这回事
  • 全局推理:LLM 在摄入时就跨整个语料建立关联,而非查询时缝合碎片
  • 知识复利:每次摄入和每个好答案都让知识库更厚,价值随时间累积
  • 零基建:纯 Markdown + 文件夹,Git 可版本化,Obsidian 可直接打开
  • 可审计:人随时能读懂、修改知识库本身;log.md 记录全部操作
  • 矛盾显性化:冲突被主动检测并交给人裁决,而非被悄悄混进答案

✦ 局限与代价

  • 规模天花板:甜蜜区约 10 万 token 的精选语料;百万级文档仍是 RAG 的主场
  • 摄入昂贵且慢:每个新来源要 LLM 通读并更新 10+ 页面,分钟级延迟 + 真金白银的 token
  • 错误会累积:LLM 维护出错(误读、错链、过度概括)会固化进知识层,需要 Lint 和人工抽查兜底
  • 不适合实时数据:高频变化的内容(行情、日志、工单流)写入成本无法摊销
  • 依赖强模型:摄入质量 = 知识库质量,弱模型会产出劣质 Wiki
  • 模式尚年轻:缺乏成熟评测基准,最佳实践仍在社区摸索中

08 · 从零实现

最小可行 LLM Wiki:一个文件夹就够了

这个模式最迷人的地方在于:最小实现不需要写一行代码。 一个文件夹、一份 Schema、一个 Agent(如 Claude Code),三件套即可启动。

建目录

创建 raw/ 与 wiki/ 两个文件夹,把要研究的文档丢进 raw/。

写 Schema(CLAUDE.md)

用自然语言写下规则:页面类型、命名约定、wikilink 用法、Ingest/Query/Lint 的操作步骤。这是整个系统唯一的"代码"。

执行 Ingest

对 Agent 说:"摄入 raw/xxx.pdf"。它会按 Schema 读源、建页、织链、记日志。

日常 Query + 定期 Lint

提问让它读 Wiki 作答并沉淀好答案;每隔一段时间跑一次 Lint 体检。用 Obsidian 浏览,用 Git 做版本控制。

Schema 最小示例(CLAUDE.md)

# 本目录是一个 LLM Wiki。你是它唯一的维护者。

## 结构
- raw/        原始来源,只读,永不修改
- wiki/       你维护的知识层
  - index.md  全部页面的目录,每次操作后更新
  - log.md    操作日志,格式:- YYYY-MM-DD [操作] 摘要
  - sources/  每个来源一个摘要页,引用注明 raw/ 路径与位置
  - concepts/ 概念页 · entities/ 实体页 · synthesis/ 综合页

## 约定
- 页面间引用一律用 [[wikilink]];提到尚不存在的页面也先建链
- 每页 YAML frontmatter:title / type / sources / updated
- 发现与已有内容矛盾时,不要擅自取舍,在页面顶部用
  > ⚠️ CONFLICT 块标出双方说法及来源,等待人工裁决

## 操作
- ingest <file>:通读 → 建摘要页 → 更新所有相关页(通常 10+)→ 记 log
- query <问题>:只读 wiki/ 作答并给引用;答案有沉淀价值时写成新页面
- lint:全库体检,报告矛盾、死链、孤儿页、知识缺口
前端:Obsidian(可选) 采集:Obsidian Web Clipper 动态视图:Dataview 插件 出片:Marp 版本与协作:Git Agent:Claude Code / 任意 CLI Agent

需要更多工程能力时再升级:要图谱可视化和混合检索 → 参考 nashsu/llm_wiki; 要让 Claude Desktop 通过 MCP 直接操作工作区 → 参考 lucasastorian/llmwiki。 模式是模块化的——按需取用,无需全盘照搬。
